# ADR-001. Выбор архитектуры серверной части

**Дата:** 2026-11-04  
**Статус:** Принято для проектирования

**Контекст:**

Word Hunt включает авторизацию пользователей, распознавание фотографий, создание карточек, работу со словарём, тренировки и сбор статистики. Необходимо выбрать, как организовать серверную часть приложения.

**Ограничения:**

- Проект разрабатывается небольшой командой.
- На начальном этапе нет необходимости независимо запускать и масштабировать каждую функцию.
- Код разных функций должен быть разделён, чтобы изменения в одном месте не затрагивали без необходимости остальные части.
- Архитектура должна позволять в будущем отдельно вынести наиболее нагруженную часть, например распознавание фотографий.

**Рассмотренные варианты:**

1. **Обычный монолит:** всё серверное приложение запускается как одна программа. Код можно разделять по папкам и классам, но строгие границы между частями системы не обязательны.
2. **Модульный монолит:** тоже одно приложение, но оно заранее разделено на модули с отдельными обязанностями. Модули взаимодействуют через определённые интерфейсы.
3. **Микросервисы:** крупные функции реализуются как отдельные приложения и взаимодействуют друг с другом по сети. Их можно запускать на одном физическом сервере, например на одном VPS, но каждый сервис всё равно нужно отдельно настраивать, запускать и связывать с другими.

**Решение:**

Выбран модульный монолит.

**Обоснование:**

- **Подходит для масштаба проекта:** Word Hunt пока не требует независимого запуска и масштабирования каждой функции.
- **Понятное разделение кода:** авторизация, распознавание, словарь и обучение будут находиться в отдельных модулях.
- **Проще разработка и запуск:** достаточно разрабатывать и развёртывать одно backend-приложение. Не нужно настраивать сетевое взаимодействие между несколькими собственными сервисами.
- **Возможность развития:** если распознавание в будущем станет создавать большую нагрузку, его можно будет вынести в отдельное приложение и увеличивать его мощности независимо от остальных функций.

**Недостатки решения:**

- Нельзя независимо развернуть или обновить один модуль — обычно обновляется всё приложение.
- При высокой нагрузке на один модуль масштабировать придётся весь backend.
- Если не соблюдать границы модулей, код может превратиться в обычный монолит с тесно связанными частями.
- Сбой backend может затронуть все его функции.

**Последствия:**

- Серверную часть необходимо разделить на модули: авторизация, распознавание, словарь и коллекции, тренировки, статистика.
- Модули должны обращаться друг к другу через заранее определённые интерфейсы, а не использовать внутренний код друг друга напрямую.
- Для MVP используется одно развёртываемое backend-приложение.
