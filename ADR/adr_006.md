# ADR-006. Управление сохранением карточки и временной фотографии

**Дата:** 2026-11-04  
**Статус:** Принято для проектирования

**Контекст:**

После фотосъёмки и получения результата распознавания пользователь может изменить слово, перевод либо отменить операцию. Карточка не должна сохраняться в словаре до явного подтверждения. При этом необходимо определить статус самой фотографии в промежутке между распознаванием нейросетью и нажатием кнопки создания карточки.

**Ограничения:**

- Экран проверки и возможность ручного редактирования обязательны перед сохранением (ФТ-10–16).
- Отказ от сохранения или закрытие приложения не должны засорять постоянное хранилище (ФТ-14, НФТ-3, 7–8, 11).
- Фотографии и реляционные данные хранятся раздельно, поэтому откат транзакции БД не удаляет физический файл автоматически.

**Рассмотренные варианты:**

1. **Хранение фотографии только на клиенте до сохранения:** фотография передаётся на сервер для распознавания, но не сохраняется на backend; при подтверждении клиент загружает файл повторно.
2. **Временное хранение фотографии на сервере:** файл сразу сохраняется на сервере с временным статусом и привязкой к пользователю. При подтверждении файл переводится в постоянное хранилище и связывается с карточкой, а невостребованные файлы удаляются фоновым процессом.

**Решение:**

Выбрано временное хранение фотографии на сервере (Вариант 2).

**Обоснование:**

- **Экономия трафика и времени:** исключается повторная загрузка тяжёлого графического файла с мобильного устройства при нестабильном соединении.
- **Контроль состояния:** карточка создаётся только при явном подтверждении, что предотвращает появление мусорных записей в словаре.
- **Изоляция данных:** временный файл закрепляется за идентификатором текущего пользователя, что исключает доступ посторонних лиц к загруженным снимкам.

**Недостатки решения:**

- Необходимость реализации механизма фоновой очистки неиспользованных временных файлов.
- Риск рассогласования: при сбое транзакции создания карточки в БД остаётся постоянный файл в файловом хранилище, требующий компенсации.
- Необходимость проверки идемпотентности при повторной отправке одного и того же идентификатора временного фото.

**Последствия:**

- Сервер принимает фото, сохраняет его во временное хранилище и возвращает клиенту `temp_photo_id` вместе с результатами распознавания.
- Запрос создания карточки обязательно передаёт `temp_photo_id`; backend проверяет владельца, переносит файл в постоянное хранилище и создаёт запись карточки в БД.
- Настраивается регламент автоматического удаления временных файлов с истекшим сроком жизни.
