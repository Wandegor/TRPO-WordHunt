# ADR-009. Стандартизация формата ответов об ошибках API

**Дата:** 2026-11-04  
**Статус:** Принято для проектирования

**Контекст:**

В процессе работы приложения возможны сетевые задержки, сбои сервиса распознавания, ошибки валидации и отказы в сохранении записей. Мобильный клиент должен однозначно интерпретировать тип проблемы и информировать пользователя без аварийного завершения работы.

**Ограничения:**

- Ошибка распознавания или сети не должна приводить к падению приложения (НФТ-11).
- Нераспознанный объект должен давать возможность повторить съёмку или ввести слово вручную (НФТ-12).
- Ошибки сохранения должны чётко отделяться от успешного создания карточки (НФТ-3, 13).
- Запрет на утечку трассировок стека, ключей доступа и системной информации во фронтенд (НФТ-7–8).

**Рассмотренные варианты:**

1. **Индивидуальный формат ошибок для каждого метода:** разрозненные структуры и текстовые сообщения, требующие частных обработчиков в мобильном клиенте.
2. **Стандартные коды состояния HTTP с унифицированным JSON-телом ошибки:** использование статусов HTTP (4xx, 5xx) в сочетании со строгой схемой ответа, содержащей машиночитаемый код и понятный текст.

**Решение:**

Выбрано использование стандартных кодов состояния HTTP с унифицированным JSON-телом ошибки (Вариант 2).

**Обоснование:**

- **Единый контракт:** клиентское приложение реализует централизованный перехватчик (interceptor) для типизированной обработки сетевых и бизнес-ошибок.
- **Предсказуемое поведение UI:** разделение статусов позволяет отличить отсутствие авторизации (401) от бизнес-ситуации, когда нейросеть не выявила объект (успешный ответ со специальным флагом либо 422).
- **Безопасность:** детализированные логи остаются во внутренней системе мониторинга сервера, а клиент получает только безопасное публичное сообщение.

**Недостатки решения:**

- Необходимость строгого проектирования и документирования каталога кодов ошибок для команды разработки.
- Требование аккуратной классификации: необходимо различать сбой инфраструктуры и штатный отрицательный бизнес-результат.

**Последствия:**

- В API утверждается единый формат тела ошибки: `{"code": "<ERROR_CODE>", "message": "<Описание>"}`.
- Для методов API закрепляются стандартные HTTP-статусы: 400/422 (ошибка валидации), 401 (требуется вход), 403/404 (доступ запрещён/не найдено), 500/503 (внутренний сбой/недоступность сервиса распознавания).
- Мобильный клиент при получении ошибок сохранения не переводит карточку в статус созданной.
