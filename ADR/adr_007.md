# ADR-007. Аутентификация и разграничение доступа к ресурсам

**Дата:** 2026-11-04  
**Статус:** Принято для проектирования

**Контекст:**

Каждый пользователь приложения обладает персональным словарём, коллекциями и фотографиями. Знание идентификатора чужой карточки или ссылки на фото не должно давать возможность просматривать, модифицировать или удалять чужие данные. Необходимо определить механизм идентификации клиента и авторизации запросов к API.

**Ограничения:**

- Наличие регистрации и авторизации пользователей (ФТ-1).
- Защита личных данных, изображений и словарей от несанкционированного доступа (НФТ-7, НФТ-8).
- Взаимодействие мобильного клиента с backend выполняется по защищённому протоколу HTTPS.
- Для MVP необходим простой способ мгновенного отзыва сессии при выходе из учётной записи.

**Рассмотренные варианты:**

1. **JWT (JSON Web Token):** автономная проверка подписи токена на сервере без обращения к хранилищу сессий, но со сложной процедурой немедленного отзыва.
2. **Серверные сессии со случайным токеном:** выдача случайной строки с сохранением состояния сессии (или её хеша) на стороне backend и возможностью моментального удаления при выходе.

**Решение:**

Выбраны серверные сессии со случайным токеном (Вариант 2).

**Обоснование:**

- **Управляемость сессиями:** выход пользователя из системы мгновенно аннулирует токен на сервере без необходимости вести списки блокировок (blacklists).
- **Простота реализации для MVP:** логика проверки валидности токена и времени его жизни прозрачна и надёжна в рамках модульного монолита.
- **Изоляция доступа:** личность пользователя устанавливается строго сервером; клиентский `user_id` из тела запроса не принимается в качестве доказательства владения ресурсом.

**Недостатки решения:**

- На каждый входящий запрос требуется обращение к хранилищу сессий для проверки токена.
- Необходимость фоновой очистки просроченных сессий в базе данных.

**Последствия:**

- Backend при успешном входе генерирует непрозрачный токен с ограниченным сроком действия; клиент сохраняет его в защищённом хранилище мобильной ОС.
- Все запросы на выборку, изменение и удаление данных (`cards`, `collections`, `photos`) выполняют фильтрацию строго по `user_id`, полученному из текущей сессии.
- Попытка доступа к чужому ресурсу блокируется с возвратом ошибки авторизации.
