# ADR-003. Выбор базы данных для хранения информации

**Дата:** 2026-11-04  
**Статус:** Принято для проектирования

**Контекст:**

Word Hunt должен хранить пользователей, карточки, коллекции и результаты тренировок. Эти данные связаны между собой: карточка принадлежит пользователю, входит в словарь и может участвовать в тренировках. Необходимо выбрать базу данных для их хранения.

**Ограничения:**

- Данные имеют понятные связи: пользователь владеет карточками, карточки могут входить в коллекции, а результаты тренировок относятся к карточкам и пользователям.
- С базой данных одновременно будут работать разные пользователи через backend.
- Необходимо поддерживать целостность данных, чтобы карточки и результаты не ссылались на несуществующие записи.
- Команда уже имеет опыт работы с PostgreSQL.

**Рассмотренные варианты:**

1. **SQLite:** реляционная база данных, которая обычно хранится в одном файле и не требует отдельного сервера. Подходит для небольших приложений и прототипов. Поддерживает одновременное чтение, но запись в каждый момент времени выполняется только одним процессом.
2. **MongoDB:** документоориентированная база данных, в которой информация хранится в виде документов, похожих на JSON. Подходит для данных с гибкой и часто меняющейся структурой.
3. **PostgreSQL:** реляционная база данных, которая работает как отдельный сервер и поддерживает таблицы, связи, ограничения и транзакции. Рассчитана на работу с несколькими одновременными подключениями и операциями.

**Решение:**

Выбрана PostgreSQL для хранения структурированных данных приложения.

**Обоснование:**

- **Связи между данными:** PostgreSQL позволяет связать пользователей, карточки, коллекции и результаты тренировок с помощью таблиц и внешних ключей.
- **Одновременная работа пользователей:** PostgreSQL подходит для общей серверной базы, к которой одновременно обращаются разные пользователи. В отличие от SQLite, она не ограничивает запись одним писателем в каждый момент времени.
- **Надёжность:** транзакции позволяют выполнять несколько изменений как одну операцию — либо все изменения сохраняются, либо операция откатывается.
- **Опыт команды:** ранее мы уже работали с PostgreSQL, поэтому сможем быстрее приступить к разработке без дополнительного изучения новой СУБД.

**Недостатки решения:**

- PostgreSQL нужно отдельно установить и настроить.
- При изменении структуры таблиц потребуется выполнять миграции.
- Для быстрой работы больших выборок могут понадобиться индексы и оптимизация запросов.

**Последствия:**

- Для хранения пользователей, карточек, коллекций и результатов тренировок будут созданы отдельные таблицы.
- Связи между таблицами будут заданы с помощью ключей.
- Фотографии не будут храниться в самой базе данных: для них используется отдельное файловое хранилище (ADR-004).
- Для защиты от потери данных необходимо настроить резервное копирование (ADR-010).
